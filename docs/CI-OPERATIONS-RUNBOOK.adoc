= CI, security and deployment operations

This runbook distinguishes a scanner taking time from a workflow that is queued,
not starting, failing during analysis, or unable to publish results. Do not use
one generic label such as "CodeQL is slow" for those different conditions.

== CodeQL: current diagnosis and change

The recent evidence separates three different conditions:

. PR #3 CodeQL run `36409629916` was `startup_failure`, attributed to
  `arena-ai-coding-agent[bot]`, with zero jobs. This is not a slow query.
. The post-merge main run `36405799171` did start: setup, checkout, and
  initialization succeeded; `Perform CodeQL Analysis` failed. It ran from
  09:48:12 to 09:51:08 UTC (about three minutes total), not hours.
. The GitHub code-scanning analyses API returns HTTP 403 with
  `Code Security must be enabled for this repository to use code scanning`.
  The active `EstateBranching` ruleset nevertheless requires CodeQL results at
  `high_or_higher`. This is a configuration/entitlement deadlock until the
  owner enables Code Security or changes the policy intentionally. The run log
  for the failed analysis was unavailable to this integration; inspect it in
  the Actions UI before attributing the exact step failure to that 403.

The live `main` workflow matrix analyzes only `actions`, despite this repository
containing `scripts/check-action-pinning.js` and standalone Rust tools. PR #3
proposes covering `actions`, `javascript-typescript`, and `rust` in three
parallel no-build jobs. That candidate configuration is not yet merged or
validated by a successful PR workflow. Idris source is not included in CodeQL's
supported language set and must not be represented as covered by this workflow.

CodeQL languages are independently supported on GitHub; ensure the chosen
language identifiers and no-build modes remain supported when upgrading the
pinned CodeQL action. Keep the SHA in `codeql.yml` and the corresponding
`actions.lock` dependency/workflow edge identical in any future action update.

== How to diagnose a slow or missing run

First separate *queue latency* from *execution time*. For a run ID:

[source,bash]
----
R=metadatastician/ziz
ID=<run-id>
gh api "repos/$R/actions/runs/$ID" --jq '{event,actor:.actor.login,triggering_actor:.triggering_actor.login,status,created_at,run_started_at,updated_at,conclusion,head_sha,html_url}'
gh api "repos/$R/actions/runs/$ID/jobs" --jq '.jobs[] | {name,status,conclusion,started_at,completed_at,steps:[.steps[]|{name,conclusion,started_at,completed_at}]}'
----

Interpretation:

* `queued`/`requested` for a long time, or large gap before `run_started_at`:
  inspect Actions minutes/billing, concurrency contention, runner availability,
  approval requirements, workflow enablement and event permissions. This is not
  CodeQL query execution time.
* `startup_failure` with zero jobs: inspect the run's event/triggering actor,
  the Actions workflow validation message, reusable-workflow reachability and
  `actions.lock` ↔ `uses:` equality. There is no CodeQL analysis to optimize.
* Jobs start and one step takes a long time: inspect that job's step timings and
  CodeQL logs. Compare checkout, initialization/database creation, query, and
  upload separately; inspect languages, query suites, build mode, source volume,
  generated/test exclusions, and runner resources. Do not reduce query coverage
  before identifying the expensive stage.
* Analysis finishes but the run/check stays red or the ruleset stays blocked:
  distinguish SARIF upload/Code Security entitlement, alert processing, and
  required-check name mismatches. Verify an analysis exists in the code-scanning
  API/UI for the exact commit.
* A check is green but a scan was skipped due to missing secret/token: report it
  as *not configured*, not *scanned*.

For any report of an overnight/day-long delay, capture the run ID and compare
creation, job start, step start/end and analysis ingestion timestamps. That
identifies whether the delay belongs to GitHub's queue, a runner, the analyzer,
or result processing.

== Recommended gate/deploy layers

* Pull request fast gates: lock-sync, deterministic build/tests, secret scanning,
  and CodeQL on the supported languages once Code Security is enabled. Keep
  required checks limited to stable emitted check/job names and test each before
  adding it to a live ruleset.
* Advisory PR signals: CodeRabbit and quality/score tools can inform review, but
  should not block deployment unless their service, policy and failure semantics
  are understood and reliably available.
* Main branch: rerun checks on the exact merged SHA and retain the result links.
  A PR merge is not proof that post-merge scans succeeded.
* Deployment: configure GitHub Pages' `github-pages` environment restrictions
  and required reviewers/branch rules in repository settings; protect release
  tags and ensure a release is made only from a reviewed, passing commit. Those
  environment/ruleset controls live on GitHub, not in workflow YAML alone.
  Container CI remains opt-in until an owned runner is present.
* Runtime: this is a repository/template and static site, not a deployed
  long-running service. Do not invent runtime monitoring checks where there is
  no service. Add health/observability checks only when a real deployed target
  exists.

== Owner actions not available to this integration

The authenticated GitHub App token reports no repository `admin`, `maintain`,
`push`, or `pull` permission; attempts to delete a branch in the other owner's
repository returned 403. It cannot enable repository Code Security, alter live
ruleset/app settings, configure SonarCloud/GitGuardian/Semgrep projects, enable
native auto-merge, or set deployment-environment restrictions. Those are owner
or organization administrator settings, not changes that can be made by editing
this repository. The exact owner actions should be recorded with before/after
checks once someone with the relevant access applies them.
